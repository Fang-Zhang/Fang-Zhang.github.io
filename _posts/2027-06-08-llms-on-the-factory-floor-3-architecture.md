## What this post finds

Parts 1 and 2 picked a model and adapted it. Part 3 is about where it sits. The public evidence on this question is thin, and almost all of it concerns one task, generating PLC (programmable logic controller) code in the IEC 61131-3 Structured Text language, because that is where a wrong answer moves machinery. Two recent papers carry the argument.

- **A local model can match the cloud on compile rate.** [Kersting, Rummel and Benndorf](https://arxiv.org/abs/2511.09122) built a Mitsubishi Electric code assistant and tested eight configurations on 100 queries each. A fine-tuned 16B model with retrieval compiled 86 percent of programs, and cloud GPT-5 with retrieval 87 percent. The intervals overlap.
- **Compiling is a weak gate.** [PLCWorld](https://arxiv.org/abs/2610.02982) (Kim and colleagues, 2026) runs generated programs in a simulated plant. For GPT-5.5, task success falls from 82.70 percent on easy cases to 25.10 percent on hard ones, and on hard motion-control tasks the safety-violation rate is 65 percent.
- **Extra verification loops cost more and did not reliably help.** Four adapted generate-and-verify frameworks used more model calls, tokens and time than direct generation, without consistent plant-level gains.
- **The model's latency rules out the control loop.** Median generation time was 5.9 seconds at the fastest and over 450 seconds for a multi-agent framework; a controller scans in milliseconds.

## What the two studies measured

**The local assistant (Kersting et al., November 2025).** The system lets several models compete in a chat interface and compiles each program on a server running the vendor's engineering software (GX Works3), returning structured errors for repair. The cloud models were GPT-4.1 and GPT-5 on Azure (GPT-5 with low reasoning effort, tested after the project ended); the local model was DeepSeek Coder V2 Lite, a 16-billion-parameter model that in quantised form used about 10 GB and fits on a laptop. Training data for the local model was synthetic: programs generated by the GPT-4.1 retrieval pipeline and kept only if they compiled and passed static checks. The paper's stated reason for going local is that its industry partners do not trust cloud providers with control logic.

What the authors report, in their words and numbers:

- Compile rate of the local fine-tuned model without retrieval equalled cloud GPT-4.1 with retrieval (73 percent each).
- The retrieval version of the local model was slow enough that the system prompt had to be shortened to keep answers under a minute.
- Users still preferred the larger model, which explained its code and wrote better-structured programs. Fine-tuning had made the local model unlearn explanations. Some compiled programs were not sensible: empty arrays and misused functions compile without error.
- The authors call compilation "necessary but not sufficient" and require review by a qualified automation engineer before any deployment.

**The plant simulator (Kim et al., 2026).** PLCWorld has 100 synthetic tasks and 473 task-condition pairs in two suites, Motion Control and Material Handling. A program is run against a simulated plant at its scan period, and the evaluator records task success and safety violation separately. Six models and four frameworks were tested. The paper states that its safety metric covers specified constraints in evaluated conditions and is not a safety certification, and that physical deployment needs independent engineering review.

## What re-scoring the published numbers shows

The script below uses only numbers printed in the two papers. It runs no model.

```python
# Re-scoring published numbers from two papers on LLM-generated PLC code (Kersting et al. 2025; Kim et al. 2026). No new model runs.
import math
def wilson(k, n, z=1.96):
    p = k / n; d = 1 + z * z / n
    c = (p + z * z / (2 * n)) / d; h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return c - h, c + h

print("=== Check 1: 100 queries per configuration (Kersting et al.): how well separated are the compile rates? ===")
cfg = [("Azure GPT-5 + retrieval", 87), ("Local fine-tuned + retrieval", 86), ("Azure GPT-4.1 + retrieval", 73), ("Local fine-tuned", 73),
       ("Azure GPT-5", 56), ("Azure GPT-4.1", 38), ("Local base + retrieval", 25), ("Local base", 23)]
ivs = {}
for name, k in cfg:
    lo, hi = wilson(k, 100); ivs[name] = (lo, hi)
    print(f"{name:30s} {k:3d}%  95% interval {lo*100:4.1f} to {hi*100:4.1f}")
a, b = ivs["Azure GPT-5 + retrieval"], ivs["Local fine-tuned + retrieval"]
print(f"top two overlap: {a[0] < b[1] and b[0] < a[1]}; GPT-5 + retrieval vs GPT-4.1 + retrieval overlap: {ivs['Azure GPT-5 + retrieval'][0] < ivs['Azure GPT-4.1 + retrieval'][1]}")
print("(two-sample difference test for 87 vs 86 of 100: ", end="")
p1, p2 = .87, .86; se = math.sqrt(p1*(1-p1)/100 + p2*(1-p2)/100); print(f"z = {(p1-p2)/se:.2f})")

print()
print("=== Check 2: two ways to rank the same models (Kim et al., PLCWorld, 1,419 task-condition cases per model) ===")
rows = {"GPT-5.5": (1399, 869), "Gemini 3.8 Flash": (1187, 806)}
for m, (acc, clean) in rows.items():
    print(f"{m}: accepted by the upstream check {acc}/1419 = {acc/1419:.1%}; clean (success, no violation) among accepted = {clean/acc:.1%} so execution gap {1-clean/acc:.1%}; clean among all cases {clean/1419:.1%}")
print("paper reports execution gaps 37.88 and 32.10 -> the recomputation above matches; the lower gap belongs to the model with fewer clean outcomes")

print()
print("=== Check 3: where a model can sit relative to the control loop (generation time per task, Kim et al. Table 4 medians) ===")
for m, s in (("GPT-4o", 5.90), ("Gemini 3.8 Flash", 65.54), ("GPT-5.5", 99.29), ("Claude Sonnet 5", 122.32), ("Agents4PLC (GPT-5.5)", 452.56)):
    print(f"{m:22s} {s:7.1f} s per task = " + ", ".join(f"{s/ (p/1000):,.0f} scans at {p} ms" for p in (10, 100)))
print("(scan periods of 10 and 100 ms are illustrative inputs, not values from the paper)")

```

- **A benchmark of 100 queries cannot rank the top two.** The 87 and 86 percent compile rates differ by 0.21 standard errors. The interval for GPT-5 with retrieval (79 to 92 percent) overlaps the one for the local model (78 to 92 percent), and just reaches into the GPT-4.1 retrieval interval (64 to 81 percent). The solid claim is the tier: retrieval or fine-tuning moved the compile rate from the 23 to 56 percent range to above 70 percent.
- **The ranking depends on the metric.** Gemini 3.8 Flash has a lower execution gap than GPT-5.5 (32.1 against 37.9 percent, reproduced from the counts), but the upstream check accepts only 83.7 percent of its programs against 98.6 percent, so it ends with fewer clean runs: 56.8 against 61.2 percent of all cases. The paper makes the same point in its own words: a lower execution gap alone does not imply a better outcome.
- **Task success and safety are separate columns.** On hard material-handling tasks Gemini 3.1 Pro scores higher task success than GPT-5.5 (35.25 against 27.87 percent) and a higher violation rate (51.95 against 32.24 percent).
- **Generation time is incompatible with a loop.** At an illustrative 10 ms scan period, the fastest median generation (5.9 seconds) is 590 scans. The scan periods are inputs chosen here, not values from the paper.
- **What was not checked.** The two studies use different vendors, tasks and metrics, so their numbers are not combined here. PLCWorld tasks are synthetic, and its verification frameworks are the benchmark authors' adaptations with GPT-5.5 as backbone, not the original tools.

## What this means for architecture

1. **Put the model beside the loop, never in it.** Both studies use the model as an engineering assistant that proposes code. A person and a deterministic toolchain stay between the suggestion and the controller.
2. **Gate on behaviour, not on syntax.** Compile success is the cheapest check and the weakest. A simulation with separate success and safety scores catches what a compiler does not, and in PLCWorld the hard tasks, defined by wider control-dependency scope, are where success collapses.
3. **Choose where it runs by what must stay on site.** Where control logic is a trade secret, a quantised model of around 16 billion parameters on an engineering workstation is a tested option for one vendor dialect, not a general result. Where it is not, the hosted model gave better explanations and needed no local training.
4. **Budget latency per task, not per token.** A median of one to two minutes per generation is acceptable for an engineer waiting on a draft and impossible for anything reactive.
5. **Treat extra agent loops as a measured option.** In PLCWorld the heaviest framework used 18 calls and over 500,000 tokens per task at median, with no consistent improvement over a single call.
6. **Keep sign-off human.** Both papers say so, and the simulator's authors state that passing it is not certification.
